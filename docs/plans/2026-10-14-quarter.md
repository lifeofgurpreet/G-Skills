# G-Skills: 14 October 2026 → 14 January 2027

**Owner: Gurpreet.** This is a three-calendar-month execution plan, not a promise
of unattended agents, scheduled jobs or automatic releases. Named task owners
are responsibility roles; target dates are planning checkpoints. The native Beads
graph is the only task-state authority. Both the [collection roadmap](../../ROADMAP.md)
and [VPS Health roadmap](../skills/vps-health/ROADMAP.md) now display its owners,
target dates, states and dependencies.

G-Skills remains a collection of independent useful skills. VPS Health is the
first entry, not the collection's runtime, version or product identity. A future
skill does not inherit its Linux worker, dashboards or provider policies.

## The outcome we are building toward

A user gives a supported coding agent a complete skill and a goal. The agent
resolves authorized targets, executes routine setup, verifies actual results,
handles missing access and leaves a usable handoff. The human provides scope,
authentication and consequential approvals—not hand-written config or shell work.

A narrow, honestly supported preview can be ready before every optional feature
is complete. The calendar must not become a reason to postpone useful sharing
forever, or a reason to call an unqualified feature ready. Public announcements
and invitations remain a separate owner decision.

## Month one — dependable first use

**Collection plan and distribution:** `gs-nah.1` owns this plan. `gs-nah.5` implements the reversible selected-archive lifecycle, while `gs-nah.2` separately qualifies
clean installation, interrupted upgrade, rollback and removal without overwriting
another skill, user changes, observations or credentials. Existing archive tests
are a baseline, not proof that a client discovers the installed skill correctly.

**Immediate runtime correction:** `gs-2uh.10` fixes matching Prometheus routes being
rejected when an agent repeats the same setup after workspace creation. Changed
endpoints, inventory and credential-variable names must remain refusals. Omitted
inputs reuse retained configuration and do not require the original profile file.

**Cold and resumed client journeys:** `gs-2uh.11` provides a private artifact
evaluator; `gs-2uh.6` uses it with actual authorized Codex and Claude Code sessions.
Required scenarios are clean demo setup, a missing-target clarification rather
than measuring the agent machine by assumption, retained-workspace reuse, a
separate session continuing the same run, verified stop, and a tool/permission gap
that is reported rather than bypassed. Count routine work handed back to the human
separately from necessary consent questions. Target: no human-written config or
command copying in the supported happy path, not zero human authority.

The evaluator checks installed bytes, real process identity, HTTP readback and
retained observations. A model saying "done" is insufficient. Equally, driving the
evaluator with deterministic Python fixtures is not a real-client trial. Pair
artifact receipts with the private native trace and semantic review. A reported
client name or installed executable version cannot satisfy this gate.

Basic monitoring does not require Gmail. The old dependency making cold-client
work wait for connector integration is removed. Missing-connector handling can be
tested without OAuth; actual access and writes remain `gs-2uh.4` and `gs-2uh.5`.

**Safety and sustained use:** `gs-2uh.12` reviews private-state, partial-setup and
upgrade boundaries. `gs-2uh.8` runs explicitly approved passive 72-hour pilots with
collection interruptions and recovery retained. Qualify a no-stack Linux route
and an existing-monitoring route before claiming both. Target at least 90% valid
coverage per configured subject, no lost observations and truthful missing/stale
states. This is a pilot-quality target, not a new CPU threshold or VPS entitlement.
A synthetic three-day dataset and a worker configured for three days do not count
as a completed three-day field trial.

## Month two — broaden only what is verifiable

`gs-2uh.4` verifies actual host-native connector discovery and authentication only
when a requested task needs it, including absent, declined, revoked and
session-specific access. `gs-2uh.5` then qualifies recipient/thread/content binding
and uncertain external-write recovery through an explicitly authorized test route.
A local request/result record cannot become OAuth proof or sending permission.
No provider is contacted just to demonstrate a workflow.

`gs-2uh.7` qualifies remote access and platform scope: Linux worker, actual user
browser, approved tunnel or remote viewer, reconnect and stop. A listener on the
VPS is not proof that the user can reach its localhost URL. Do not expose a public
listener, change firewall settings or install a root service to hide the gap.
Windows/macOS may be control/viewing environments without supporting Linux local
counter collection or the managed Linux lifecycle.

`gs-8cq.5` adds provider references only after dated primary-source checks of exact
product, allocation and usage distinctions. The supplied reviews' additional
supplier names are research scope, not implemented policies or automatic provider
identification. Preserve the unknown/other route and distinguish plan allowance,
measured delivery, baseline and contractual commitment.

`gs-8cq.3` designs separately approved CPU, memory and storage experiments. Define
the actual question, target filesystem, bounded time/bytes/operations, relevant
versions, load confounds, measurement divisor, stop conditions and failed-run
retention before execution. Fsync quantiles need sample-size uncertainty; hashing
throughput is not IPC or physical-host attestation. Active experiments are optional,
not prerequisites for a passive-monitoring preview.

## Month three — share responsibly and learn from use

`gs-nah.3` prepares a small community preview with supported recipes, known limits,
a synthetic walkthrough, reproducible bug reports, private-data warnings and a
maintainer triage path. A public repository and source releases already exist;
social posts, invitations and email still require a distinct Gurpreet decision.

`gs-2uh.9` turns repeated agent/field friction into the smallest owning regression
and reviewed fix. Prefer removing confusing steps over adding another coordinator.
Learning must not weaken thresholds, collect extra private material, acquire
permissions or publish captures automatically.

`gs-8cq.4` qualifies broader authorized SSH/path diagnostics after remote estate
handling: exact hosts/destinations, bounded concurrency, timeouts, partial results,
missing dependencies and unmeasured assets. Presence in an SSH config is not
blanket authorization. Packet loss and softnet counts alone are not provider proof.

`gs-nah.4` proposes at most three useful repeated workflows for the next independent
skill and obtains Gurpreet's selection. Define its outcome, authority and cold-use
acceptance before scaffolding. No selected problem means an explicit pending
product decision—not a fake second live skill to fill the catalog.

`gs-2uh.13` is the VPS-specific preview gate. Its native blocking dependencies are
`gs-2uh.6`, `gs-2uh.8`, `gs-2uh.12` and `gs-nah.2`; it cannot be closed while those
acceptance tasks remain open. Unrelated future skills are not held behind it.

Review these against current task evidence, not this document's age. There is no
automatic publishing mechanism here and no test count that replaces the review.

| Claim | Required evidence | Owning tasks |

Every provider, mail sending, every operating system and active benchmarks are not
required for a narrow preview **when excluded from its advertised support**. Each
needs separate qualification before the claim expands. An unresolved privacy,
evidence-loss or authority defect stops expansion regardless of target dates.

## Work-in-progress and next-session rules

At most three concurrent streams: one collection task, one primary skill
implementation and one verification/research task. Reconcile live GitHub and Beads
before starting; finish or block one high-impact item before opening another large
branch. Keep existing IDs and explain dependency changes instead of duplicating work.

Each session records exact source, what ran, what failed, what was not tested and
the next safe action. Source tests, native-client behavior, deployed configuration
and sustained outcomes are different evidence classes. A blocked authentication
or execution boundary is not permission to weaken safeguards. Monthly checkpoints
may reorder or reduce scope based on evidence. This plan schedules no background
agent, reminder, social post or provider action.
