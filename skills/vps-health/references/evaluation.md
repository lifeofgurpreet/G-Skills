# Evaluate whether a coding agent can actually use this skill

This is an optional maintainer workflow, not a prerequisite for someone monitoring
a VPS. Keep evaluation fixtures separate from their real servers, accounts and
observations. The agent does routine execution; the human reviews meaningful
results and authorizes any real access.

## Four different tests

**Discovery metadata:** the actual YAML header must parse and its name/version
must match the manifest. The public 0.9.3 description contained an unquoted colon
and failed Anthropic's skill-creator validator. This is fixed in 0.9.4 and covered
by a collection regression. A passing code suite is not a substitute for this
check. Parsing alone does not establish that every client's trigger logic works.

**Artifact behavior:** `evals/evals.json` uses Anthropic's skill-creator structure.
The three cases cover sparse-context interpretation, a useful local software-support
draft and reconciliation of an unknown email delivery outcome. All inputs are
explicitly synthetic. The expected files and fields are specified in the prompt;
a grader must not penalize reasonable output based on hidden requirements.

**Trigger selection:** `evals/trigger-evals.json` has 20 realistic positive and
adjacent-negative queries. They exercise the discovery description, not the
runtime's CPU policy. These queries have not yet been executed as a trigger
benchmark. Do not infer a trigger score from their existence or rewrite a description
until testing separates overtriggering from undertriggering.

**Real operations:** fresh CLI installation, actual bounded worker start/resume/stop,
remote browser access and current connector results have separate acceptance.
The existing `tools/skills/vps-health/client_journey.py` checks runtime artifacts.
A file-reading/drafting eval does not certify those workflows or a 72-hour pilot.

## Run comparable trials

Freeze the published baseline and the candidate. Start independent private
workspaces with identical tasks, inputs, tools, permissions and budgets; use the
old skill for a baseline when improving an existing skill. Keep the grader and
held-out tasks outside the executor's accessible inputs. Excluding tests/evals
from the executor snapshot should be identical in both conditions and recorded.

Use the user's existing authorized model/client route. Do not change accounts,
copy credentials, weaken the sandbox or grant a tool merely to obtain a pass.
Record the actual client/model, trace, tool results, timestamps, tokens and output
artifacts. Missing token counters are unknown, not output-character estimates.
Separate environment/authentication failures from model mistakes. Stop dispatch
when a shared client environment is blocked instead of repeatedly hitting the
same expired session. Native Claude
may return a result whose subtype is success but is_error is true; that is not
successful inference.

The prepared tasks can run with native Read/Write tools in a restricted synthetic
workspace. They need no real mail, Bash, provider API or new host measurements.
A future operational eval must explicitly authorize its bounded operation and
use the actual runtime checker; do not re-label a restricted artifact trial as
full autonomous bootstrap.

## Grade results, then inspect them

From the development repository, the agent runs:

```bash
python3 tools/skills/vps-health/grade_agent_eval.py \
  --run /private/iteration-1/eval-1/with_skill/run-1 --eval-id 1 \
  --out /private/assessment.json
```

The grader checks real files, numeric coverage, explicit outcome flags and a
completed native trace. A blocked or zero-inference run returns
BLOCKED_OR_NO_INFERENCE with no behavioral summary; a run that used inference but ended early remains
INCOMPLETE_EXECUTION. Neither may be silently discarded. Successful artifact checks
still require semantic review: did the explanation invent facts, hand routine
work back to the human, confuse the recipient, or pretend a tool ran?

The grader's expectations use `text`, `passed` and `evidence`, compatible with the
official skill-creator review workflow. Preserve failed/blocked trials in the
coverage report. Do not omit blocked conditions and then advertise a perfect
pass rate. Do not average a partial set into an old/new improvement claim.

Use Anthropic's reviewed `eval-viewer/generate_review.py --static` for a portable
review page rather than maintaining another custom evaluation UI. Keep raw native
traces private. A sanitized page for blocked attempts should say that its status
cards were generated by the harness, not the model, and should have no invented
benchmark. Only aggregate paired completed runs; record the actual repetition
count instead of a default supplied by a reporting script. One run is not a
reliability estimate. Subjective output comparisons need human calibration.

## Improve without overfitting

Convert failures into the owning regression, a clearer instruction or a reusable
helper already justified by repeated work. Re-run old/new tasks after the change,
plus the regression suite. Do not duplicate the monitoring service, optimize only
for the three fixtures, loosen evidence thresholds, self-grant permissions or
publish private traces. A new model/version should earn the same acceptance.

Current execution status is in the repository's
`docs/skills/vps-health/agent-eval-proof-v0.9.4.json`. The first six native old/new
attempts could not refresh their existing OAuth session; they stopped before
inference with no artifacts, no external action and no behavioral score. Native
reauthentication is required before those comparisons can complete. The metadata
fix, fixture/grader tests and actual package checks are independent delivered work.
